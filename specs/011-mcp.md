# 011 — Integración MCP sobre la API de control

## Contexto

El simulador ya expone una API de control HTTP (`ControlServer.java`: `/health`, `/session`,
`/abonos/*`, `/test-runs/*`) pensada para disparar y observar corridas de prueba con clientes
HTTP simples. Un servidor MCP envolvería esa misma API (más lo que se agregue por las specs
001-010) como herramientas con esquema propio, disponibles para cualquier agente/cliente
compatible con MCP sin tener que re-explicar la API cada vez.

## Requisitos

Por decidir en el diseño detallado — este documento cubre la arquitectura general, no el
detalle de cada herramienta todavía.

## Fuera de alcance

- Reemplazar la API de control HTTP existente — el MCP la envuelve, no la sustituye. Los
  `httpclient/*.http` y el uso directo por `curl` siguen funcionando igual.

## Diseño propuesto (a discutir)

- Un servidor MCP que expone como herramientas, como mínimo, lo que ya existe: disparar
  abonos/escenarios, consultar sesión, consultar corridas y eventos.
- Conforme las specs 001-010 agreguen parámetros nuevos a la API (particionado, variaciones de
  red, tipos de devolución, etc.), las herramientas MCP correspondientes crecen junto con ellas
  — no se diseñan por adelantado sin la API que envuelven ya definida.

## Convención sobre granularidad de specs de MCP

Esta spec cubre la arquitectura/decisión general (sí se implementa, envuelve la API existente).
Si conforme se detalla van apareciendo grupos de herramientas con alcance y dependencias
claramente distintas entre sí (ej. "disparar escenarios" vs. "diagnóstico de corridas fallidas"
vs. "configurar variaciones de red"), esos grupos se separan en specs propias numeradas
(`012-mcp-...`, `013-mcp-...`) el mismo criterio que ya se usó para separar 002/003/004 del
brainstorm original — no se decide de antemano cuántas specs de MCP van a existir, se separan
cuando el alcance diverge lo suficiente para justificarlo.

## Decisiones de arquitectura (2026-09-21, implementadas)

- **Sin autenticación propia** — hereda el mismo nivel de acceso que la API de control HTTP hoy.
  Confirmado el 2026-09-28 (ver "Decisiones cerradas").
- **Proceso aparte**, no en el mismo proceso Java del simulador — `mcp-server/` (Node.js), habla
  con la API de control por HTTP igual que cualquier otro cliente (`curl`, `httpclient/*.http`).
  Configurable vía `SIMULATOR_URL`.
- Todo lo del brainstorm original (diagnóstico automático, fuzzing, autoría en lenguaje natural)
  **no** es parte de esta spec — queda pendiente de numeración propia una vez evaluado.

## Despliegue junto a la API y distribución como plugin (2026-09-28, implementado)

Decisión de Miguel Zavala: quien prueba solo debe descargar el skill, sin clonar el repo.

- **El MCP corre junto a la API**, como segundo servicio de `docker-compose.yml`
  (`banxico-simulator-mcp`), en modo **Streamable HTTP sin estado** en `:8090/mcp`. Habla con la
  API por la red interna de compose. Se despliega con la misma versión del repo que la API, así que
  herramientas y endpoints no se desincronizan (el 2026-09-28 se encontró el host corriendo una
  API anterior a `/abonos`, `/abonos/carga` y `/heartbeat/detener` mientras el MCP ya las ofrecía).
- **El modo stdio se conserva** solo para desarrollo local (`MCP_TRANSPORT` sin definir).
- **Distribución:** plugin de Claude Code en `plugin/` (skill `spei-network-fault-injection` +
  `.mcp.json` con `"type": "http"`), publicado por el marketplace de un solo plugin en
  `.claude-plugin/marketplace.json`. La URL se ajusta con `BANXICO_SIM_MCP_URL` (default
  `http://192.168.1.200:8090/mcp`).
- Se retiran el `.mcp.json` de la raíz y `mcp-server/start.sh` (el MCP local por stdio que
  lanzaba cada Claude Code abierto en el repo). El skill se mueve de `.claude/skills/` a
  `plugin/skills/`; quien trabaja en el repo instala el mismo plugin.
- Los nombres de herramienta para permisos pasan a
  `mcp__plugin_banxico-simulator_simulador__<herramienta>`.

## Estado de implementación

`mcp-server/` (Node.js + `@modelcontextprotocol/sdk` 1.31) expone 11 herramientas, 1:1 con los
endpoints de la API de control. Probado el 2026-09-28 contra el simulador real en
`192.168.1.200`, en los dos transportes y dentro de su contenedor: `initialize`, `tools/list` y
`simulator_health`/`simulator_session` respondieron con datos reales. **Pendiente de desplegar**
en el host (ver criterios).

## Decisiones cerradas

- ~~¿La ausencia de autenticación propia sigue siendo aceptable?~~ Sí: la VPN hacia la red del
  simulador es la frontera de confianza, igual para la API y para el MCP (2026-09-28). Si el MCP
  llegara a exponerse fuera de esa red, esta decisión se reabre.

## Criterios de aceptación

- [x] Existe un servidor MCP que expone como herramientas lo que ya existe en la API de control.
- [x] Probado de extremo a extremo contra una instancia real del simulador (no solo localhost).
- [x] El MCP corre en modo HTTP en su propio contenedor junto a la API (probado localmente
      contra la API real).
- [x] El plugin y el marketplace pasan `claude plugin validate`.
- [ ] Desplegado en el host: `http://192.168.1.200:8090/mcp` responde y el plugin instalado desde
      el marketplace lista las herramientas.
- [ ] Las herramientas correspondientes a 001/003/005/007/010 se agregan conforme esas specs
      añadan los endpoints que las respaldan.
